# Master Decision Log

This file documents every non-trivial implementation decision made on the Sales-Connections platform. Per the user-supplied Explainability rule, rationale lives here, never in code comments. Each decision is a single row in the table below; rows are appended in chronological order and never edited destructively. Superseded decisions retain their original row with a "Superseded By" reference to the new ADR.

## How to Use This Log

### Authoring conventions

- ATX-style headers are used throughout this document; a single space follows each `#`.
- The decision log is a single Markdown table with eight columns: `ID`, `Decision`, `Alternatives Considered`, `Rationale`, `Risks`, `Date`, `Status`, `Superseded By`.
- IDs follow the pattern `DL-NNNN` (DL for Decision Log; zero-padded 4-digit sequence; never reused).
- Rows are appended in chronological order (oldest first); the freshest decisions are reached via Ctrl-End.
- Each cell uses `<br>` for in-cell line breaks when more than one bullet point is required.
- No emoji are used anywhere in this document.
- Decisions whose rationale spans multiple paragraphs use a footnote reference of the form `[^DL-NNNN]` and a footnote block at the end of the document.
- The table is intentionally wide; viewers should use a Markdown editor that supports horizontal scrolling.

### When to add a row

- Any architectural decision (framework, library, design pattern).
- Any non-trivial business-logic decision (for example, why outreach status mutation excludes Contributors).
- Any operational decision (deploy strategy, secret rotation cadence, alarm threshold, retention window).
- Any decision that a future contributor might reasonably question with the words "why did we do it this way?".

### When NOT to add a row

- Routine code-style decisions where the project simply adopts the tool's defaults (for example, ruff and prettier defaults with no project-specific override) do not require an entry; convention is assumed.
- Trivial mechanical refactors (rename a variable, extract a method, split a file for readability) carry no architectural rationale and require no entry.
- Decisions fully derived from the AAP without selection (for example, "we use Flask 3.1.3 because the AAP §0.3.2 mandates it") need no entry; the AAP itself is the rationale and is referenced by other entries that did require a selection.

### Format

- Append a new row to the main table below. Do not insert rows in the middle.
- Choose the next available `DL-NNNN` ID; IDs are never reused, even when a decision is superseded.
- Fill in all eight columns; mark `Superseded By` as `—` (em dash) for newly accepted decisions.
- Date in ISO 8601 (`YYYY-MM-DD`).
- Status is one of: `Accepted`, `Proposed`, `Rejected`, `Superseded`.

### Superseding a decision

- Add a new row with the new decision; reference the old `DL-NNNN` in the new row's Rationale cell.
- Edit the old row's `Status` cell from `Accepted` to `Superseded` and fill its `Superseded By` cell with the new `DL-NNNN`.
- Do NOT delete the old row. The decision log is append-only for the same reason the audit table is append-only: history must be reconstructible without consulting git.
